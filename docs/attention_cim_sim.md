# Attention CIM AV Dataflow Simulator

`attention_cim_sim.py` is a standard-library-only ablation simulator for AV
MatMul dataflow in CIM-based Transformer accelerators.

It is **not** an exact TP-DCIM reproduction. The goal is to make dataflow
assumptions explicit enough to compare:

1. paper-like HIVA/V-stationary underutilization,
2. resource-matched HIVA/V-stationary with one `V_j` active at a time,
3. optional HIVA parallel-`j` upper bound,
4. VIHA/A-stationary ping-pong,
5. V-generation hiding under finite V buffering,
6. array-write and input-feed overheads.

## Background Model

The simulator targets:

```text
Z = A x V
A: N x N
V: N x D
block op: Z_i += A_i,j x V_j
```

Default blocking:

```text
A row tile       = 192
reduction tile   = 64
V output tile    = 64
R = ceil(N / A row tile)
C = ceil(N / reduction tile)
O = ceil(D / V output tile)
```

The logical AV tile count is:

```text
R * C * O
```

Default resource budget:

```text
total CIM engines = 6
QKG / AV engines = 4
VG / V-generation engines = 2
```

## Action Names

Each engine records one visible action per cycle:

```text
IDLE
WRITE_A_ARRAY   # VIHA: write A block into QKG CIM array
WRITE_V_ARRAY   # HIVA: write or replicate V block into QKG CIM array
LOAD_A_INPUT    # HIVA: stream A block into CIM input drivers
LOAD_V_INPUT    # VIHA: stream V block into CIM input drivers
LOAD_X_INPUT    # VG: load X or pX part for V generation
VGEN_COMPUTE
AV_COMPUTE
```

## V Generation

V generation is modeled as tiled partial computations. By default:

```text
model_dim = 768
vg_reduction_tile = 128
vgen_parts_per_v = ceil(768 / 128) = 6
```

This follows the paper description where tiled `V_j` is divided into partial
`pV_j` matrices generated by:

```text
pX_j(64 x 128) x pW_j(128 x 64)
```

So `6` is not a universal fixed cycle count. It is a tiling count, and each part
has configurable latency:

```text
--write-x-cycles-per-part
--vgen-cycles-per-part
```

Timeline details use labels such as:

```text
V[c0,o0] p0/6
V[c0,o0] p1/6
...
V[c0,o0] p5/6
```

## Finite V Buffer

The paper architecture includes an 8KB V buffer. The simulator models this with:

```text
bytes_per_element = 1
v_tile_bytes = reduction_tile * v_output_tile * bytes_per_element
v_buffer_bytes = 8192
v_buffer_capacity_blocks = max(1, v_buffer_bytes // v_tile_bytes)
```

With the default `64 x 64 INT8` V tile:

```text
v_tile_bytes = 4096
v_buffer_capacity_blocks = 2
```

The simulator therefore does not allow unlimited V pre-generation. It tracks:

```text
max_v_buffer_occupancy_blocks
v_buffer_full_stall_cycles
qkg_wait_for_v_cycles
```

The buffer model is an explicit producer-consumer approximation, not a
cycle-perfect NoC/SRAM model.

## Implemented Schedules

### `hiva_paper_like`

Weak Fig. 1(c)-style V-stationary baseline:

- one QKG/AV engine stores `V_j`,
- one WV/VG engine generates V,
- the AV engine sweeps all `A_i,j` row blocks for that `V_j`,
- `LOAD_A_INPUT` is counted for HIVA A streaming,
- V generation can hide only within the finite V buffer.

### `hiva_resource_matched_j_serial`

This is the intended fair HIVA resource-matched baseline:

- one `V_j` is processed at a time,
- `V_j` is written into QKG CIM array,
- if `replicate_v=True`, `V_j` is replicated across all 4 QKG engines,
- `v_replication_bandwidth` controls how many QKG engines receive the V write in
  the same write interval,
- the A row-block sweep for that same `V_j` is parallelized across QKG engines,
- each A row-block uses `LOAD_A_INPUT` then `AV_COMPUTE`,
- only after all row blocks for `V_j` finish does the model consume `V_j` and
  move to `V_{j+1}`.

This replaces the earlier over-optimistic default that processed different
`V_j` blocks on different QKG engines in parallel.

### `hiva_resource_matched_parallel_j_upper_bound`

Optional optimistic upper bound, enabled only with:

```bash
--include-parallel-j-upper-bound
```

It allows different `V_j` blocks to be processed by different QKG engines in
parallel. This assumes enough partial-sum accumulation bandwidth and should not
be used as the fair HIVA baseline.

### VIHA Modes

Select with:

```bash
--viha-mode pingpong
--viha-mode prefetch_a_upper_bound
--viha-mode serial
```

`pingpong` is the default paper-like A/B-C/D mode:

- QKG engines are split into two groups:
  - group0: QKG0, QKG1
  - group1: QKG2, QKG3
- one group computes while the other writes the next A blocks,
- A writes use `WRITE_A_ARRAY`,
- V feed can be modeled with `LOAD_V_INPUT`,
- if the needed `V_j` is not in the finite V buffer, QKG waits.

`prefetch_a_upper_bound` assumes A blocks are already prefetched or A writes are
fully hidden, so all 4 QKG engines can compute. This is optimistic.

`serial` loads A and computes without ping-pong, to expose the ping-pong benefit.

## Usage

Run default N=2048:

```bash
python attention_cim_sim.py
```

Run paper-size examples:

```bash
python attention_cim_sim.py --N 1024
python attention_cim_sim.py --N 2048
python attention_cim_sim.py --N 4096
```

Run with the optional parallel-`j` HIVA upper bound:

```bash
python attention_cim_sim.py --N 2048 --include-parallel-j-upper-bound
```

Try VIHA sensitivity modes:

```bash
python attention_cim_sim.py --N 2048 --viha-mode pingpong
python attention_cim_sim.py --N 2048 --viha-mode prefetch_a_upper_bound
python attention_cim_sim.py --N 2048 --viha-mode serial
```

Sweep default paper-like parameters:

```bash
python sweep_attention_cim_sim.py \
  --N-list 1024 2048 4096 \
  --v-replication-bandwidth-list 1 2 4
```

Sweep V generation and buffer sensitivity:

```bash
python sweep_attention_cim_sim.py \
  --N-list 1024 2048 4096 \
  --model-dim-list 768 \
  --vg-reduction-tile-list 128 \
  --vgen-parts-per-v-list auto \
  --v-buffer-bytes-list 4096 8192 16384 \
  --write-x-cycles-per-part-list 1 2 \
  --vgen-cycles-per-part-list 1 2 \
  --hiva-a-input-load-cycles-list 1 2 \
  --viha-mode-list pingpong serial prefetch_a_upper_bound
```

By default, outputs are saved to:

```text
outputs/attention_cim_sim_N{N}_metrics.csv
outputs/attention_cim_sim_N{N}_timeline.csv
outputs/attention_cim_sim_N{N}_engine_breakdown.csv
outputs/attention_cim_param_sweep.csv
```

You can override paths:

```bash
python attention_cim_sim.py \
  --N 2048 \
  --metrics-csv results/hw_av_metrics_N2048.csv \
  --timeline-csv results/hw_av_timeline_N2048.csv \
  --breakdown-csv results/hw_av_engine_breakdown_N2048.csv
```

## Caveats

- This is a deterministic ablation model, not a cycle-accurate hardware model.
- It does not model detailed NoC contention, SRAM banking, analog MAC timing,
  ADC/DAC latency, or detailed CIM peripheral cost.
- It assumes fixed per-tile write, input-feed, and compute latencies.
- Hidden overlap assumptions are simplified because the timeline stores one
  visible action per engine per cycle.
- The normalized utilization values are trend/debugging aids, not exact Fig. 11
  reproduction claims.
